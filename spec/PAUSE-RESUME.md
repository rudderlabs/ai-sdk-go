# Paused runs and task starts

Since v0.4. These additions are declared in `ai-events-v0.4.schema.json` and `ai-client-events-v0.2.schema.json`. SDK `SPEC_VERSION` is `0.4.0`; the migration checker accepts both 0.3.0 and 0.4.0 captures.

A run has one interaction ID and one prompt event. Every pause sends `ai_response_received` with `response_status: paused` and a `pause_reason`. Resuming keeps the IDs and starts a new segment; it sends neither another prompt nor another task-started event. A final end is idempotent. `end` with an explicit or derived paused status behaves like `pause`; a repeated pause before a resume sends nothing. A model or tool call recorded while paused resumes the interaction automatically.

Each response contains only that segment's model/tool counts, tokens, costs, usage and tool breakdown, latency and first-token timing. Summing responses counts each call once. Only the final response adds `pause_count` (positive integer) and `total_paused_ms` (nonnegative integer). Paused time runs from each pause to its resume, or final end while paused, and is excluded from segment latency. A client may report a rendered pause with the same ID and `response_status: paused`; counters and usage remain server-owned.

`pause` returns a JSON snapshot (`PausedInteraction` in Node and Go, a dict in Python), or no snapshot after a final end. Store it alongside the application's job state and pass it as the `resume` option of the next interaction/task. This supports worker restarts and waits lasting days. Each SDK uses the same snake_case keys:

| Required key | Meaning |
| --- | --- |
| `interaction_id`, `conversation_id` | Nonempty run IDs, reused on every segment |
| `trigger` | `user` or `system` |
| `pause_count` | Positive integer, including this pause |
| `total_paused_ms` | Nonnegative integer, waits before this pause |
| `paused_at` | Nonnegative integer, Unix milliseconds at the current pause |

Optional selection objects: `primary` has `model` (string), optional `provider` (string), `calls` (nonnegative safe integer report count), and optional `persistent` (boolean, true to survive later calls). `outcome_hint` has `status`, optional `errorType` and `pauseReason`, and `calls` (nonnegative safe integer report count); it selects the outcome only while that report count is current. All SDKs write these objects. Readers also accept the older Python lists `[provider, model, calls, persistent?]` and `[status, errorType, calls, pauseReason]`, and snake_case `error_type` / `pause_reason` in hint objects.

A snapshot with a malformed `pending_calls` or `pending_tools` field is not a paused interaction snapshot; every SDK starts a fresh interaction. Optional pending fields must be omitted when absent; JSON null is malformed.

Optional nonempty strings: `user_id`, `anonymous_id`, `feature`, `surface`, `account_id`, `on_behalf_of`, `trigger_source`, `task_name`, `trigger_event_id`, `parent_interaction_id`, `intent`, `trace_id`, `agent_version`, `variant`. Snapshot IDs, identity and run fields take precedence over arguments and request context, including fields absent from the snapshot. No prompt/response content, completed-segment calls, clients or process objects are serialized. Since v0.4, optional `pending_calls` and `pending_tools` arrays carry usage accepted after the paused response captured its totals. These records use snake_case usage/tool metadata, including call counts and known costs, and omit tool arguments and results. They enter the resumed accumulator without replaying call events. The `last` and `last_ok` call markers retain outcome/model selection; a `history_only` record retains that selection for a folded call and contributes no totals. With `emitLlmCalls`, a `history_only` record with `call_event_pending: true` and neither marker is the call event of a folded group (calls past `maxCallsPerInteraction`) that was not sent before the snapshot: it restores as that unsent event, with its `call_index`, and contributes no totals. Optional nonnegative integers `report_count` (usage reports recorded so far, which order the `last` and `last_ok` markers), `successful_call_sequence` (the report number of the latest successful call) and `pending_compactions` (compactions recorded after capture) keep outcome selection and `compaction_count` identical after JSON restoration; these counters are separate from usage totals. With `emitLlmCalls`, an optional nonnegative integer `call_sequence` (model calls reported across all segments, `callCount` summed) is written when above 0, so `ai_llm_response_received.call_index` (SDK-6798) continues after restoration; absent, a restored run starts again at 1. With `emitLlmCalls`, each `pending_calls` record also carries its optional `call_index` (positive integer), so a pending call sends the same `call_index` after restoration. A `pending_calls` record also carries an optional boolean `credits_explicit`, true when its `credits` came from the report rather than the credits hook, so a twin or repeat report recorded after restoration keeps those credits. The three SDKs write a record's twin-matching state under the same keys: booleans `from_span` (reported by a tracing span), `matched` (already merged with its twin) and `usage_known` (false for unknown or partial usage). Readers accept `started_at` and `ended_at` as finite nonnegative epoch-millisecond numbers or RFC3339 strings. Node and Python write epoch-millisecond numbers; Go keeps writing RFC3339Nano text in UTC (and omits timestamps for an untimed call), so released Go readers can restore new Go snapshots. Go will switch to epoch-millisecond numbers once released Go readers accept them. An unparseable timestamp follows the SDK's existing invalid-value rule: Node and Go warn and start a fresh interaction; Python treats that timestamp as unknown (zero). Readers also accept what was written before SDK-6111: Go's `twin_matched`, `usage_unknown`, RFC 3339 `started_at` / `ended_at` and `uncredited` (a folded group's partial `credits`, now left out instead), and Python's `started_ns` / `ended_ns` in nanoseconds. Each `pending_calls` record can carry an optional nonempty string `raw_model`: the deployed model ID of its authoritative usage, before canonicalization of `model`, used by pricing and the credits hook after restoration. All three SDKs write and read it; when absent, `model` is the fallback. All SDKs also write optional positive `report_sequence` (first-report order, separate from aggregate call counts); readers reconstruct legacy order from individual records when it is absent. Fractional pending `latency_ms` and `time_to_first_token_ms` round half up for emitted events, matching live call timing. A `pending_tools` record taken from the overflow list sets `overflow: true` and restores to the overflow list, so it emits no declared tool event. For an unfired tool whose declared event has `when` or `properties` rules, the SDK evaluates the rules at pause, outside the interaction lock, and stores the outcome in `rule_outcome`: `suppressed` (boolean), `properties` (object of rule-derived properties) and optional `result_size_bytes`. The resumed worker emits or suppresses that event from `rule_outcome` without running the rules again, so raw arguments and results never enter the snapshot. `fixtures/pause-pending-usage-v0.1.json` fixes the portable representation. Configure the resumed worker's analytics, prices and privacy policies separately. Unusable snapshots warn and start a new interaction.

A `pending_calls` record with `pricing_pending: true` holds a call whose newest revision was still being priced when pause closed its segment. That call and its held call event contribute no count, usage or credits to the paused segment; its superseded credits are omitted from the snapshot, which retains the newest pricing basis and metadata. In process, the outstanding hook result applies to the held call when it returns. A restored run invokes its own credits hook outside SDK locks before counting the call in the resumed segment. Both paths retry against newer usage or metadata up to three attempts, then omit credits with `credits_unstable`; a throwing hook omits credits with `user_callback`. The resumed segment counts the call once with its final credits, and its held call event carries those same credits. Another pause while pricing is still active holds the call again. End is synchronous: a held call whose new price is still in flight at End is counted once in the final segment without those credits, and the late result is ignored. End while paused opens a final segment for pending usage (D2), including this held call.

An older SDK restoring such a snapshot ignores `pricing_pending` and counts that call without credits. Node releases before this one cannot restore Go snapshots whose pending calls carry RFC3339 timestamps: they start a fresh interaction. Go v0.10.0 and earlier reject numeric pending-call timestamps from Node or Python and start a fresh interaction; Go keeps writing text in this release to preserve Go-to-Go restoration. An untimed snapshot isolates the marker downgrade.


Pause callbacks may reenter `pause`: Node returns `undefined`, Python returns `None`, and Go returns `ok == false` while finalization is unfinished. Go uses this in-progress result for concurrent callers too, so they can retry without blocking a callback. Python also returns `None` to a caller on another thread while a pause is in flight, so concurrent callers must retry after the first pause returns. During delivery, Go can return a completed snapshot immediately. Each snapshot reflects all writes accepted before its capture. Once segment totals are captured, later model/tool writes remain pending for the next segment, including on explicit resume or JSON restoration; repeated pauses emit no additional response.

For an in-process continuation call `resume()` on the paused interaction. TTL and shutdown never finalize a paused interaction, but it keeps counting toward the open-interaction limit until it ends; resuming it in process, or restoring its snapshot in the process that paused it, always succeeds, while a snapshot from another process goes through normal admission. Returning normally from an interaction/task leaves a paused run paused; an exception still sends a final error. An abandoned paused run retains its last paused event.

Pause timestamps use the wall clock so cross-process waits can be measured; negative elapsed time after clock skew is clamped to zero. Snapshots do not coordinate workers: persist them reliably and serialize approval deliveries per job. Replaying a snapshot in two workers can produce duplicate segments; transport delivery and application job state remain the app's responsibility.

`ai_task_started` is optional and off by default (`emitTaskStarted`, `emit_task_started`, `WithTaskStartedEvents`). It is sent before a new task's work and contains `conversation_id`, `interaction_id`, `task_name`, and supplied `trigger_source` and `parent_interaction_id`, plus the run's background fields. Resumes and ordinary interactions send none. A task start without a final response identifies an in-flight or abandoned run; its most recent paused response identifies a wait.

`fixtures/conformance-v0.4.json` covers repeated pauses, explicit and implicit resumes, persisted snapshots, no-ops, final ends while paused and chained task starts. Approval-loop examples in each SDK demonstrate three worker invocations separated by two approvals.

With `emitSpans`, snapshots preserve an internal `sdk_trace_id` independently of application `trace_id`, and pending calls preserve `span_id`. JSON restore publishes pending product events with their join IDs without replaying spans. Overflow calls omit span IDs.

Per-call content follows the binary sanitization rules in `fixtures/FIXTURE-FORMAT.md`. Go exception (SDK-6948): with `emit_spans` off, a value's own `MarshalJSON` or `MarshalText` output is stripped as plain data; bytes that the marshaler encodes as ordinary text, including base64, can reach per-call content. Pause snapshots still omit captured per-call content.
