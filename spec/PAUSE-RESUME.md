# Paused runs and task starts

Since v0.4. These additions are declared in `ai-events-v0.4.schema.json` and `ai-client-events-v0.2.schema.json`. SDK `SPEC_VERSION` is `0.4.0`; the migration checker accepts both 0.3.0 and 0.4.0 captures.

A run has one interaction ID and one prompt event. Every pause sends `ai_response_received` with `response_status: paused` and a `pause_reason`. Resuming keeps the IDs and starts a new segment; it sends neither another prompt nor another task-started event. A final end is idempotent. `end` with an explicit or derived paused status behaves like `pause`; a repeated pause before a resume sends nothing. A model or tool call recorded while paused resumes the interaction automatically.

Each response contains only that segment's model/tool counts, tokens, costs, usage and tool breakdown, latency and first-token timing. Summing responses counts each call once. Only the final response adds `pause_count` (positive integer) and `total_paused_ms` (nonnegative integer). Paused time runs from each pause to its resume, or final end while paused, and is excluded from segment latency. A client may report a rendered pause with the same ID and `response_status: paused`; counters and usage remain server-owned.

A tool call that a pause waits on, such as one awaiting approval, is counted in the segment that runs it. When first recorded, each tool call takes an agent key: its own `agent_name`, else the `agent_name` of the latest model call recorded before it in the segment (wrappers record a call's tool calls right after it), else the empty key. When a later report of a model call recorded without an agent names it (the call's span twin, or a repeat of its response ID), the call is that agent's from its own place in the order, and the tool calls that took its empty key take that agent's key. At a pause, a tool call is waiting when it has a tool-call ID, no outcome or result has been seen, its declared event has not been sent, it is not a structured-output candidate, and no model call by its agent key was recorded after it in the segment. The paused response leaves it out of `tool_call_count` and `tool_breakdown`, sends no declared event for it and computes no `rule_outcome`. It is carried into the next segment, ordered before every new call (after JSON restore, from `pending_tools`). A later record or result for its ID merges into it, so it counts once, in that segment, with its real outcome (`success`, `error` or `denied`), and its declared event is sent once. Still unresolved, it counts as `unknown` at that segment's final end, and every later pause applies the same test again. A run that never resumes never counts it, and neither does one that ends while still paused: a final end is not a resume, so a tool call the pause still waits on then is left out of the final segment and sends no declared event (one reported with an outcome while paused counts there). Tool calls without an ID, with an outcome, or from an agent's earlier calls count in the paused segment. Past `maxCallsPerInteraction`, a tool call that may be waiting (an ID, no outcome, not a structured-output candidate) is still kept, as many again at most, so that a pause can carry it. Until then it counts by identity only, with no outcome or declared event, like any tool call past the limit, and a later record or result for its ID is not counted again. Two costs follow:

- Declared-event rules that read arguments (`properties(args, result)`, `when(args, ...)`) see none after a JSON restore unless the execution record repeats them: snapshots never carry tool arguments or results.
- Wrapper-only apps never record tool results. When they pause after tools ran but before the next model call, those tools count only in the resumed segment, and never if the run is not resumed.

`pause` returns a JSON snapshot (`PausedInteraction` in Node and Go, a dict in Python), or no snapshot after a final end. Store it alongside the application's job state and pass it as the `resume` option of the next interaction/task. This supports worker restarts and waits lasting days. Each SDK uses the same snake_case keys:

| Required key | Meaning |
| --- | --- |
| `interaction_id`, `conversation_id` | Nonempty run IDs, reused on every segment |
| `trigger` | `user` or `system` |
| `pause_count` | Positive integer, including this pause |
| `total_paused_ms` | Nonnegative integer, waits before this pause |
| `paused_at` | Nonnegative integer, Unix milliseconds at the current pause |

Optional selection objects: `primary` has `model` (string), optional `provider` (string), `calls` (nonnegative safe integer report count), and optional `persistent` (boolean, true to survive later calls). `outcome_hint` has `status`, optional `errorType` and `pauseReason`, and `calls` (nonnegative safe integer report count); it selects the outcome only while that report count is current. All SDKs write these objects. Readers also accept the older Python lists `[provider, model, calls, persistent?]` and `[status, errorType, calls, pauseReason]`, and snake_case `error_type` / `pause_reason` in hint objects.

A snapshot with a malformed `pending_calls` or `pending_tools` field is not a paused interaction snapshot; every SDK starts a fresh interaction. Optional pending fields must be omitted when absent; JSON null is malformed.

Optional nonempty strings: `user_id`, `anonymous_id`, `feature`, `surface`, `account_id`, `on_behalf_of`, `trigger_source`, `task_name`, `trigger_event_id`, `parent_interaction_id`, `intent`, `trace_id`, `agent_version`, `variant`. Snapshot IDs, identity and run fields take precedence over arguments and request context, including fields absent from the snapshot. No prompt/response content, completed-segment calls, clients or process objects are serialized. Since v0.4, optional `pending_calls` and `pending_tools` arrays carry usage accepted after the paused response captured its totals; `pending_tools` also carries the tool calls the pause waits on. These records use snake_case usage/tool metadata, including call counts and known costs, and omit tool arguments and results. They enter the resumed accumulator without replaying call events. The `last` and `last_ok` call markers retain outcome/model selection; a `history_only` record retains that selection for a folded call and contributes no totals. With `emitLlmCalls`, a `history_only` record with `call_event_pending: true` and neither marker is the call event of a folded group (calls past `maxCallsPerInteraction`) that was not sent before the snapshot: it restores as that unsent event, with its `call_index`, and contributes no totals. Optional nonnegative integers `report_count` (usage reports recorded so far, which order the `last` and `last_ok` markers), `successful_call_sequence` (the report number of the latest successful call) and `pending_compactions` (compactions recorded after capture) keep outcome selection and `compaction_count` identical after JSON restoration; these counters are separate from usage totals. With `emitLlmCalls`, an optional nonnegative integer `call_sequence` (model calls reported across all segments, `callCount` summed) is written when above 0, so `ai_llm_response_received.call_index` (SDK-6798) continues after restoration; absent, a restored run starts again at 1. With `emitLlmCalls`, each `pending_calls` record also carries its optional `call_index` (positive integer), so a pending call sends the same `call_index` after restoration. Node also writes optional boolean `cost_explicit`, true when the report supplied `cost_usd`; a failed twin discards usage estimates after restoration. Legacy failed records with a cost are treated as reported amounts; legacy successful costs have unknown provenance and are omitted if a failed twin arrives. A `pending_calls` record also carries an optional boolean `credits_explicit`, true when its `credits` came from the report rather than the credits hook, so a twin or repeat report recorded after restoration keeps those credits. The three SDKs write a record's twin-matching state under the same keys: booleans `from_span` (reported by a tracing span), `matched` (already merged with its twin) and `usage_known` (false for unknown or partial usage). Readers accept `started_at` and `ended_at` as finite nonnegative epoch-millisecond numbers or RFC3339 strings. Node and Python write epoch-millisecond numbers; Go keeps writing RFC3339Nano text in UTC (and omits timestamps for an untimed call), so released Go readers can restore new Go snapshots. Go will switch to epoch-millisecond numbers once released Go readers accept them. An unparseable timestamp makes the snapshot unusable: all three SDKs warn and start a fresh interaction. Readers also accept what was written before SDK-6111: Go's `twin_matched`, `usage_unknown`, RFC 3339 `started_at` / `ended_at` and `uncredited` (a folded group's partial `credits`, now left out instead), and Python's `started_ns` / `ended_ns` in nanoseconds. Each `pending_calls` record can carry an optional nonempty string `raw_model`: the deployed model ID of its authoritative usage, before canonicalization of `model`, used by pricing and the credits hook after restoration. All three SDKs write and read it; when absent, `model` is the fallback. All SDKs also write optional positive `report_sequence` (first-report order, separate from aggregate call counts); readers reconstruct legacy order from individual records when it is absent. Fractional pending `latency_ms` and `time_to_first_token_ms` round half up for emitted events, matching live call timing. A `pending_tools` record taken from the overflow list sets `overflow: true` and restores to the overflow list, so it emits no declared tool event; one kept past the limit because it may be waiting also keeps its `tool_call_id` with `settled: false`, and restores as kept past the limit. A `pending_tools` record carries its agent key as the optional string `agent_key`: a nonempty key always, and the empty key (`""`) when the record has an `agent_name`, which a later record gave the tool call. A record without `agent_key`, as in snapshots written before this field, takes its `agent_name` (or no agent) as its key and otherwise restores as before. A record whose result was seen without an outcome (a duration-only result, a tool span) sets `result_seen: true`, so the tool call is no longer waiting after a restore either. A resumed segment, in process or restored, starts with its `pending_tools`, then the `pending_calls` in snapshot order, so both paths decide waiting tool calls alike. For an unfired tool whose declared event has `when` or `properties` rules, other than one the pause waits on once the paused response is delivered (a tool call recorded during that delivery can wait too, and one settled during it no longer does), the SDK evaluates the rules at pause, outside the interaction lock, and stores the outcome in `rule_outcome`: `suppressed` (boolean), `properties` (object of rule-derived properties) and optional `result_size_bytes`. The resumed worker emits or suppresses that event from `rule_outcome` without running the rules again, so raw arguments and results never enter the snapshot. A tool call settled while the run is still paused holds its declared event until the run goes on; pausing again returns a snapshot that stores its `rule_outcome`, evaluated with that result, so a run restored from it sends the same event. `fixtures/pause-pending-usage-v0.1.json` fixes the portable representation. Configure the resumed worker's analytics, prices and privacy policies separately. Unusable snapshots warn and start a new interaction.

Pause refuses re-entry from one of the same interaction's SDK callbacks for the same caller: credits hooks (including retries), analytics track/enqueue, redaction, before_send where available, content getters/serializers, and event-rule when/properties. It leaves the interaction unchanged and returns the existing not-paused value (`undefined` in Node, `None` in Python, `ok=false` in Go). It never throws. The error hook receives `pause_refused` with `reason: in_callback`; without a hook, the SDK warns once. Error handlers and application/task code may still pause, and callbacks for another interaction do not restrict that interaction.

Python identifies callers by thread ID and current asyncio task; Go compares the goroutine ID parsed from the first line of `runtime.Stack` at callback entry, falling back to the wait path if parsing fails. A different thread/goroutine waits on a condition for all pricing attempts, including capture repricing, to settle before pausing normally. The internal, nonconfigurable bound is **5 seconds**. At the bound, pause returns the not-paused value and reports `pause_refused` with `reason: pricing_in_flight`; nothing is paused, and late credits land in the still-open segment. Python pricing and capture hooks are synchronous and there is no async pause API. On an event-loop thread, a pause that would wait refuses immediately with `pricing_in_flight`, allowing other tasks to progress. Node pricing and callbacks are synchronous, so Node cannot reach this wait/bound path.

End never waits for pricing: a retained call whose new price is still in flight at End counts once without those credits, and the late result is ignored. Paused snapshots do not carry or restore in-flight pricing; unknown extension keys remain ignored.

Older Node releases cannot restore Go snapshots whose pending calls carry RFC3339 timestamps: they start a fresh interaction. Go v0.10.0 and earlier reject numeric pending-call timestamps from Node or Python and start a fresh interaction; Go keeps writing text in this release to preserve Go-to-Go restoration.


Pause from an SDK delivery callback reports `pause_refused` with reason `in_callback`, as above. While finalization is unfinished, concurrent Go callers return `ok == false` and Python callers return `None`; retry after the first pause returns. Eligible Go callers can obtain the completed snapshot during delivery. Pause settles call/tool delivery passes before capturing segment totals; writes accepted during those passes join the paused segment. Once totals are captured, later model/tool writes remain pending for the next segment, including on explicit resume or JSON restoration. Each snapshot reflects all writes accepted before its capture; repeated pauses emit no additional response.

For an in-process continuation call `resume()` on the paused interaction. TTL and shutdown never finalize a paused interaction, but it keeps counting toward the open-interaction limit until it ends; resuming it in process, or restoring its snapshot in the process that paused it, always succeeds, while a snapshot from another process goes through normal admission. Returning normally from an interaction/task leaves a paused run paused; an exception still sends a final error. An abandoned paused run retains its last paused event.

Pause timestamps use the wall clock so cross-process waits can be measured; negative elapsed time after clock skew is clamped to zero. Snapshots do not coordinate workers: persist them reliably and serialize approval deliveries per job. Replaying a snapshot in two workers can produce duplicate segments; transport delivery and application job state remain the app's responsibility.

`ai_task_started` is optional and off by default (`emitTaskStarted`, `emit_task_started`, `WithTaskStartedEvents`). It is sent before a new task's work and contains `conversation_id`, `interaction_id`, `task_name`, and supplied `trigger_source` and `parent_interaction_id`, plus the run's background fields. Resumes and ordinary interactions send none. A task start without a final response identifies an in-flight or abandoned run; its most recent paused response identifies a wait.

`fixtures/conformance-v0.4.json` covers repeated pauses, explicit and implicit resumes, persisted snapshots, no-ops, final ends while paused and chained task starts. Approval-loop examples in each SDK demonstrate three worker invocations separated by two approvals.

With `emitSpans`, snapshots preserve an internal `sdk_trace_id` independently of application `trace_id`, and pending calls preserve `span_id`. JSON restore publishes pending product events with their join IDs without replaying spans. Overflow calls omit span IDs.

Per-call content follows the binary sanitization rules in `fixtures/FIXTURE-FORMAT.md`. Go exception (SDK-6948): with `emit_spans` off, a value's own `MarshalJSON` or `MarshalText` output is stripped as plain data; bytes that the marshaler encodes as ordinary text, including base64, can reach per-call content. Pause snapshots still omit captured per-call content.

## Known limits

- Go and Python only: when a cancelled wrapper call restored from a snapshot carries explicit credits and its span twin later reports different explicit credits, Go and Python keep the wrapper's credits; Node takes the twin's.
- Corrupt snapshots: Node accepts some non-RFC3339 timestamp strings that `Date.parse` understands (for example `"2026-11-17"`); Python and Go reject the snapshot.
- Go only: a credits hook that changes the call's metadata and then fails (error, panic or invalid value) is retried, and the retry's credits are published; Node and Python stop at the failing attempt and omit credits.
- Manually reported twins with conflicting service tiers: the tier kept after the merge differs by SDK (Node and Go fall back to `standard`; Python keeps the faster tier), so later enrichment can reprice the call differently. Twins from instrumented providers always report the same tier.
- Node only: if a recorded tool call's `result`, `error` or `structuredCandidate` getter throws, that tool record is dropped from `tool_call_count`.
- Python only: caller-owned iterables (for example a generator passed as `tool_names`, or `server_tool_calls`) are iterated while the interaction lock is held; one that waits on another thread's `pause()` deadlocks.
